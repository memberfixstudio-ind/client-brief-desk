# Client Brief Desk — research decision

Date: 2026-11-13. Status: selected and implemented for v1.0.0. Competitor source inspection is separate from the runtime evidence in [Validation](VALIDATION.md).

**Decision.** Build a focused, GPL-2.0-or-later WordPress workflow for collecting and approving text briefs from existing clients. This is a useful open-source alternative in an established category, not a claim that client intake or approval tools do not exist. All core workflow features should work locally without paid services.

**Review and final selection.** The market-research reviewer recommended Service Noticeboard: reusable temporary-closure/delay notices with time-window preview and cache-aware rendering. That recommendation also acknowledged existing competition, including [WPFront Notification Bar](https://wordpress.org/plugins/wpfront-notification-bar/) and [Stuff & Things Business Hours](https://wordpress.org/plugins/stuff-things-business-hours/). The final product decision overrode that ranking and selected Client Brief Desk for this pass because the user prioritizes a substantial useful business workflow and portfolio breadth over another public banner tool. The reviewers did not unanimously select this direction; this is a product choice, not proof of an unmet category. Strong competition is accepted explicitly.

**Target user and outcome.** Small service businesses, consultants and web studios repeatedly requesting project requirements, website copy or change instructions. Staff reuse a brief, the client saves answers in an authenticated portal, and staff approve a specific submitted version. Both sides can see what is missing and what was accepted without reconstructing answers from message threads. Reduced administration is the intended benefit; no measured time saving is claimed.

## Shortlist

- **Lead follow-up inbox:** rejected after a separate technical reviewer found close overlap with [InboxMend](https://wordpress.org/plugins/submission-inbox/), including local submissions, ownership, due dates, notes and CSV.
- **Service Noticeboard:** the market reviewer's preferred direction; existing notification-bar and business-hours tools narrowed the opportunity.
- **Client Brief Desk:** selected for the complete authenticated save-submit-review workflow, strict account isolation and inspectable submission history. Strong existing competitors are accepted below.

The reason to build is a complete, deliberately small brief-review experience: three useful presets, text-only collection, clear revision handling and demonstrable access isolation. No individual feature is presented as exclusive. For users already served by these products, migration may offer little benefit.

## Selected v1 scope and implementation evidence

The original proposal named service, website-content and website-change briefs, a dedicated staff capability and staff-only JSON export. The chosen implementation instead provides `service`, `website` and `event` presets, uses `manage_options` for staff operations, and lets authenticated assigned clients with `read` export their own brief as JSON. Client responses and exports exclude staff notes and internal-note events. These choices are directly visible in [the API](../includes/class-api.php) and [the store](../includes/class-store.php). They supersede the earlier proposal; they are not additional release requirements. Runtime results and the environments actually tested are recorded separately in [Validation](VALIDATION.md).

1. **Staff creates a request** for an existing WordPress client account, using Service, Website or Event questions, with custom text questions and required/optional flags. Questions are copied into each request so later preset edits do not silently change it. The current backend does not edit questions or assignees after creation; duplication starts a separate request.
2. **Client saves and submits** through an authenticated portal showing only assigned requests. Saving permits incomplete answers; submission validates required answers. Submission events snapshot the questions and answers. After changes are requested, the client updates working answers and submits again; earlier snapshots remain stored. Responsive presentation is a UI acceptance requirement, not a result of this backend review.
3. **Staff reviews that exact submission**, requests changes with client-visible feedback, or approves it. Approval records the submission version, staff user and time. Staff cannot silently edit the accepted answers. Reopening creates another review cycle and retains the previous decision.
4. **Version conflicts are explicit.** Draft saves and review actions must check the expected version and current state atomically. A stale browser tab cannot overwrite newer answers or approve an obsolete submission. Preserve the user's unsaved text when reporting a conflict; repeated submission must not create duplicate versions.
5. **Due dates and progress** use the implemented states `open`, `submitted`, `changes_requested`, `approved` and `archived`, with answer counts separate from approval status. Due dates are date-only in the site timezone; no automatic email is sent. Required answers are validated on submission.
6. **Private staff notes, history and export** complete the workflow. Staff can JSON-export accessible briefs including internal notes; authenticated assigned clients can export their own brief without internal notes or internal-note events. The local JSON route currently reuses the detail response and its latest-50-event history; do not describe that as a complete archival export. The separate WordPress privacy exporter now pages through client-visible history and snapshots. Records remain on uninstall unless `CBD_DELETE_DATA` is explicitly enabled.

## Security and completion boundary

Use native WordPress authentication, `manage_options` for staff, per-request assignment checks on every client read/write/export, CSRF protection, validated inputs and escaped output. Nonces are not authorization; see [WordPress nonce guidance](https://developer.wordpress.org/apis/security/nonces/). Keep requests, drafts and notes out of public search, feeds and unauthenticated REST responses. Exclude authenticated portal responses from shared caching. Include personal-data export/erasure handling following the [WordPress privacy handbook](https://developer.wordpress.org/plugins/privacy/). These are release boundaries; source inspection alone does not verify deployment configuration or all failure paths.

Before release, verify two-client isolation, revoked access, anonymous access denial, staff-note confidentiality, stale saves, concurrent/repeated submission, obsolete approval rejection, immutable snapshots, required-answer validation, timezone boundaries, exports and keyboard/mobile use. An application-level history is not tamper-proof evidence against a database administrator.

Reuse existing WordPress accounts and core login/password recovery; do not build an account-registration or identity subsystem. No uploads, cloud/SaaS subsystem, paid-service dependency, automatic email, invitations, payment subsystem, legal-signature claims, external integrations or automatic website publishing in v1. Test with synthetic existing accounts on disposable local WordPress, with outbound mail and external HTTP blocked.

**Portfolio fit.** Separate from Access Ledger's WooCommerce entitlement diagnosis and the rejected lead follow-up concept. Demonstrates client authorization, private data boundaries, state transitions and concurrency protection through one understandable service workflow.

**Limits.** Competitor claims above are documentation-based, not runtime/security audits. ClientCopy details remain source-limited as described above. Customer demand and the value of this narrower experience remain unvalidated; account login and the lack of automatic reminders may limit adoption.
